# WARP & WEFT — 리디자인 기획

wear-in 스크롤 경험(v2)을 롱폼 에디토리얼(v3)로 전면 개편하는 기획과 진행 상태.

## 콘셉트

데님은 인디고로 염색한 날실(warp)과 흰 씨실(weft)을 3x1로 짠다. 앞면은 파랗고 안쪽은 하얗다. 빈티지 감정 단서(셀비지, 숨은 리벳, 케어 라벨, 단추 뒷면 번호)도 대부분 안쪽에 있다.

| 레이어 | 메타포 | 역할 | 우선순위 |
| --- | --- | --- | --- |
| 롱폼 에디토리얼 | 앞면 (인디고) | 사이트의 몸통. 9개 챕터 + 각주 | P0 |
| Inside Out 감정 도구 | 안쪽 (흰 씨실) | 사이트를 "뒤집으면" 나오는 숨은 층 | P1 |
| Heritage Line 커머스 | 라벨 / 태그 | 챕터·감정 결과를 상품으로 잇는 부가 층 | P2 |

## 정보 구조


### P0 마무리 (완료)

- 사실 대조: 각주 서술을 온라인 공개 자료(주로 Levi Strauss & Co. 아카이브 글)와 대조하고 정정. 출처 25개 중 22개 대조 완료, 출처 페이지에 대조 여부 표시. 정정 내역은 CASE_STUDY.md "사실 검증" 참고
- 감정 단서·연도 슬라이더의 전시 규격 경계를 자료 편차(1941~1944)에 맞게 조정
- OG 이미지를 표지 기준 PNG(1200x630)로 재생성 (`npm run assets:og`)
- v2 이미지 파이프라인 제거(`src/data/assets.ts`, generated/placeholder 이미지, 관련 스크립트·npm 스크립트·`.env.*`), v2 문서는 `docs/legacy/`로 이동
- CASE_STUDY.md를 v3 기준으로 재작성

### 배포 (완료)

- GitHub Pages를 브랜치 루트 서빙(legacy)에서 GitHub Actions 배포로 전환. 이전에는 빌드 전 소스 index.html이 서빙되어 빈 화면이었다
- Vite `base`를 `/levis-portfolio/`로, canonical·OG를 `VITE_SITE_URL` 절대 주소로
- `scripts/prerenderRoutes.ts`: 라우트 16개의 `<path>/index.html`(라우트별 head), `404.html`(noindex), `sitemap.xml` 생성. 딥 링크가 404 대신 200으로 응답. 앱은 끝 `/`를 정리

### 코드 스플리팅 (완료)

- 첫 화면 JS gzip 약 160 kB → 약 91 kB (`vendor` 79 + `index` 12)
- 챕터 본문을 `src/content/chapters/<slug>.ts`로 분리하고 메타데이터만 첫 번들에 남김
- 표지 외 페이지와 시각화 9종을 지연 로딩. GSAP(45 kB)는 스크롤 스크럽 시각화와 함께 받음. Lenis는 자체 rAF(autoRaf)로 돌고 ScrollTrigger는 불러온 뒤에 연결
- `vendor` 청크 분리로 앱 코드가 바뀌어도 라이브러리 캐시 유지
- 라우트별 HTML에 modulepreload, 링크 포인터/포커스 시 미리 불러오기, 다음 챕터 유휴 시간 미리 불러오기
- 청크 로딩 실패 시 오류 경계로 안내, 지연 로딩 페이지의 해시 대상은 나타날 때까지 기다렸다가 이동
- 라우트 전환 직후 Lenis 내부 값이 이전 페이지 기준으로 남아 해시 이동이 목표를 지나치던 문제를 수정

### Lighthouse 측정과 개선 (완료)

| 모바일 성능 | 이전 (라이브) | 이후 (로컬 빌드) | 이후 (라이브, 3회 중앙값) |
| --- | --- | --- | --- |
| 표지 | 56 | 98 | 87 (62 / 98 / 87) |
| 01 Gold & Canvas | 57 | 86 | 80 (77 / 83 / 80) |
| 03 Lot 501 | 56 | 90 | 85 (90 / 85 / 76) |
| 상품 상세 | 57 | 97 | 89 (88 / 89 / 90) |

- 로컬은 CPU 지수 약 3,500 조건. 같은 빌드도 CPU 지수가 약 1,000으로 떨어지면 68–89점으로 내려간다
- 라이브 재측정(10월 13일)은 CPU 지수 1,584–3,420으로 이전 측정(3,126–3,561)보다 대체로 낮았다. CPU 조건이 비슷했던 상품 상세(약 3,200)가 가장 깨끗한 비교다
- 데스크톱은 표지 94 → 97, 1장 87 → 100, 상품 상세 88 → 98, Lot 501 98. 접근성은 전 페이지 100(Lot 501은 96 → 100)
- 첫 화면이 9–10초에서 1.4–3.1초로 당겨지면서, 전에는 첫 화면 전에 끝나 계산되지 않던 작업이 TBT(110–520ms)로 드러났다. 아래 "모바일 레이아웃 비용"에서 줄였다
- 표지 모바일 CLS 0.046: 한글 본문 서체가 들어오며 표지 도식이 아래로 밀린다(좋음 기준 0.1 이하)
- 원인: 웹폰트(표지 31개·884KB, 렌더 차단 CSS 108KB). 폰트를 막자 56 → 98
- 조치: 폰트 CSS 비차단 로딩(preload → stylesheet), IBM Plex Sans KR 제거(인터페이스는 기기 고딕), Noto Serif KR 400만, 로딩 자리 화면 높이 이상(CLS), Fraunces 대체 서체 size-adjust(제목 줄바꿈 CLS 0.162 → 0.02), 연도 슬라이더 대비 2.27 → 약 5.3:1(접근성 100)
- 남은 감점: 캐시 수명(GitHub Pages 고정 10분)

### 모바일 레이아웃 비용 (완료, 배포됨 · 라이브 재측정 필요)

- 진단: 트레이스를 보니 스타일 재계산은 13–16ms뿐이고, 비용은 거의 레이아웃이었다. 챕터 본문 300여 요소의 첫 레이아웃 하나가 180ms(스로틀 없음)였고, 그 안은 시스템 한글 서체 파일 로딩(파일 하나 10–24MB)과 한글 글자 모양 계산(셰이핑)이 차지했다. Lighthouse 모바일은 이를 CPU 4배로 늘려 계산한다. 처음 의심했던 그라데이션 배경과 `backdrop-filter`는 페인트(약 10ms) 쪽이라 원인이 아니었다
- 조치 1, 한글 대체 서체 통일: 모노 스택이 그냥 `monospace`라 한국어 Windows에서는 굴림체(13.5MB)를 따로 읽었다. 라틴은 Consolas·Menlo, 한글은 UI 고딕(맑은 고딕 / Apple SD 고딕)으로. 제목 스택의 한글도 본문과 같은 명조로
- 조치 2, 화면 밖 블록 레이아웃 미루기: 본문 문단·인용·박스(앞 두 블록 제외), 주 목록, 표지 목차 항목에 `content-visibility: auto`. 크기는 실제 높이 중앙값
  - 각주 팝오버는 블록 밖으로 그려 잘리므로 최상위 레이어(Popover API)로 띄우고 버튼 기준 위치를 스크립트로 잡는다. DOM 위치는 그대로라 키보드 순서가 같다. popover를 지원하는 브라우저에서만 content-visibility를 켠다
  - 포커스 링이 잘리지 않게 `overflow-clip-margin: 8px`
  - 블록이 그려지거나 웹폰트가 도착하면 ScrollTrigger를 다시 잰다. 기존에는 웹폰트 도착 뒤 다시 재지 않아 스크럽 위치가 조금 어긋나 있었다(같이 고침)
  - 화면 밖 글자의 한글 웹폰트 조각은 load 뒤 유휴 시간에 미리 받아, 스크롤 중 글자가 바뀌지 않게 한다. 처음에는 첫 웹폰트 도착 직후 받았는데, Lighthouse가 이를 LCP 앞의 일로 계산해 Lot 501의 LCP가 3.2 → 5.6초로 나빠졌다
- 결과 (모바일 화면, 스로틀 없음, 5회 중앙값, 이전 → 이후)

| 페이지 | 가장 큰 레이아웃 | 레이아웃 합계 | TBT 근사(CPU 4배) |
| --- | --- | --- | --- |
| 03 Lot 501 | 107 → 69ms | 220 → 179ms | 597 → 425ms |
| 01 Gold & Canvas | 103 → 62ms | 221 → 180ms | 588 → 453ms |
| 02 The Patent | 121 → 88ms | 237 → 209ms | 675 → 568ms |
| 표지 | 127 → 111ms | 246 → 241ms | 641 → 591ms |

- 로컬 Lighthouse(모바일)에서 CPU 지수가 비슷한 회차끼리 보면 챕터 페이지 TBT가 1장 259·170 → 136·87ms, Lot 501 213·173 → 67·95ms, 성능 87–90 → 90–92. LCP(3.2초)와 CLS는 그대로. 표지와 상품 상세는 차이가 거의 없다
- 검증: 각주 팝오버(데스크톱 위치·잘림 없음·스크롤 추적, 모바일 하단 시트, Tab·Escape), 포커스 링, 스크럽 위치(이전 빌드를 다시 잰 값과 같음), 스크롤 중 새 웹폰트 로딩 없음, 위아래 스크롤 레이아웃 이동 0

### 표지 첫 페인트 경합 (완료, 배포됨)

- 증상: 라이브 표지가 회차마다 62점과 90–99점으로 갈렸다. 62점 회차는 웹폰트 CSS가 JS보다 먼저 도착해 첫 렌더 전에 적용됐고, 첫 화면이 웹폰트를 다 받은 뒤에야 그려졌다(관측 FCP 1.5–2.5초). Lighthouse는 그 폰트 다운로드까지 첫 화면 시간에 넣었다. 비동기 폰트 로딩으로 바꾼 뒤부터 있었다
- 조치: index.html은 폰트 CSS를 preload로 받아 두기만 하고, 앱이 첫 화면을 그린 뒤 stylesheet로 바꾼다(`src/editorial/webFonts.ts`, 백그라운드 탭은 1초 뒤 적용). 첫 레이아웃에 웹폰트 규칙 140개가 끼지 않는다
- 확인: JS를 800ms 늦춰 폰트 CSS가 먼저 오게 하면, 이전에는 첫 페인트가 CSS 적용 뒤 0.2–0.25초 더 걸렸고, 지금은 JS 실행 직후 그려진 다음 CSS가 적용된다. 웹폰트는 이후 정상으로 모두 적용(Noto Serif KR 조각 17개). CLS·권장사항 점수 변화 없음
- 대가: 웹폰트로 바뀌는 시점이 첫 화면 뒤로 고정된다(빠른 회차에서는 원래 그랬다)
- 라이브(10월 13일 배포 후): 표지 모바일 10회 모두 87–95점, FCP 5초가 넘는 회차 0회(이전 두 번의 라이브 측정에서는 9회 중 3회가 62점). 측정 PC의 CPU 지수가 900–1,400이던 때라 점수 자체는 낮게 나왔다. 같은 CPU 조건의 이전 배포와 비교하면 1장·Lot 501·상품 상세는 차이가 없다(잡음 범위)

### AI 느낌 줄이기 1단계 (완료)

AI로 만든 티가 나는 지점을 점검해 세 단계로 나눴다. 1단계는 손이 덜 가는 감점 요인 정리다.

- 숨은 층 암시를 줄임: 표지 서문, 03장 박스("이 디테일들을 기억해 두세요"), 06장 박스("안쪽을 보는 사람들"), 08장 마지막 문장, 상품 상세 힌트, 콜로폰의 Inside out 설명, 실밥 알림의 "바지 안쪽에 무언가 있습니다"를 지움. 09장 끝과 푸터 버튼만 남김
- 첫 문단 드롭캡 제거(9장 중 5장에서 숫자 "1"·"2"에 걸렸다)
- 영어 장식 라벨을 한글로: Contents→목차, Notes→주, Previous/Next→이전/다음, Sources→출처, Colophon→사이트 소개, Clue→단서, 도식 안의 영어 라벨, 장 연도 표기(Dye, Weave, Today). 고유명(WARP & WEFT, 장 제목, Heritage Line, Inside out)은 유지
- 말장난 문구 정리: "읽은 시대를 입다.", "Unravelled.", "Issue 501", 장 키커(Migration, Invention…) 삭제. 상점이 사이트를 "이 책"이라 부르던 호칭도 정리
- 섹션 라벨은 표지와 장 첫 화면에만. CTA 화살표(→) 제거, 알약 모양 버튼 15곳을 각진 모서리로(원형은 각주 번호와 장바구니 수량만)
- 표지 서문을 비유 대신 장 구성 안내로 다시 씀. 배경의 큰 연도는 숫자 구간인 장에만
- 읽는 시간을 실제 분량으로 다시 계산: 합계 41분 → 19분 (본문 글자 수 ÷ 분당 500자 + 시각화마다 1분)
- "롱폼", "모든 사실 서술에 각주", "직접 그린 도식" 같은 과장 표현 정리(일부 문단에는 각주가 없다)
- 쓰이지 않던 디자인 토큰 45개(110개 중)와 v2 구조를 가리키던 주석 정리

2단계(원고 편집)와 3단계(본인 손이 필요한 일)는 아래 남은 일에 적었다.
